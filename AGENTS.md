# Class101 for webOS (class101-for-webos)

Unofficial LG webOS TV app for CLASS101 with its own TV screens (Preact). It talks to Class101's backend directly: Firebase Auth + the Class101 GraphQL gateway. User-facing docs (Korean) are in README.md; the UI is Korean.

## Target

- Reference TV: LG OLED55CX (2020), webOS 5.6.2, web engine Chromium 68. Developer Mode device name `tv` (override with `TV_DEVICE`).
- Build target chrome53 (webOS 4+). esbuild lowers syntax; `src/app/polyfills.js` (core-js) fills built-ins. Check with `npm run check:compat` (also checks the media worker bundle).
- Packaged web apps on webOS run without CORS/mixed-content enforcement (a file:// app can fetch class101.net, googleapis and LAN http). Desktop browsers do enforce it, so tests use a same-origin mock.

- GraphQL: `https://cdn-production-gateway.class101.net/graphql`, header `authorization: Bearer <Firebase ID token>`, `accept-language: ko`. Its WAF challenges requests without a User-Agent (browsers and curl pass). Strip the site's client-only directives (`@merge`, `@relayPagination`) or the gateway rejects the document.
- Operations used (src/app/api.js): `viewer.takingClasses`, `lastClass`, `klassById { chaptersV2 { lectures } }`, `lectureV2ById { videoUrl canAccess }`, `lesson { video { progressSeconds } captions }`, `class(classId, marked: true) { lastLesson }`, `setLessonProgress`, the watching reports below, `searchProductsV5`, `categoryProductsV4`, `trendingSearchTermsV2`, `popularCategories`. Class.id == klassId; lesson id == lecture id. A class's `progressRatio` is a percentage, 0–100: the share of completed lectures (reference account: 11 of 44 done → 25). A lesson's `video.progressRatio` is 0–1. A class's `lastLesson` (also `lastClass.lastLesson`) is the lesson whose position was saved last. On the reference TV, opening another lecture (view history and `enterLecture` both succeeded) left it unchanged, and a 3 s `setLessonProgress` moved it at once.
- Watching: what class101.net's lecture page reports (bundle of Nov 21, 2026). v0.6.3 and older only saved the position, and 내 클래스 progress didn't change after watching on the TV. v0.6.4 also sends these (src/app/screens/Player.jsx):
  - Opening a lecture: `updateUserViewHistory(klassId, missionId: lectureId)` and `enterLecture(klassTicketId, missionId)`; the ticket comes from `getKlassTicketByKlassId` (cached per account and class once found). Like the site, the two are independent and finish even after the player closes; visits go out one after another, in opening order. They move the class's last-watched time (`lastClass.lastAccessedAt`), not its last lesson.
  - 10 s after opening and after each change of the playing state (`playing` / `pause` events, as on the site), one at a time: `updateLectureViewHistory(sessionId, klassId, lectureId, videoPlayed)`. It returns the session id (a UUID) to send the next time; on error the site doubles the wait. Leave `sessionId` out of the variables until there is one: an explicit `null` gets INTERNAL_SERVER_ERROR "Cannot return null for non-nullable field Mutation.updateLectureViewHistory".
  - Every 10 s of lecture played, counted in content seconds; the sampling baseline restarts on `seeking`, `seeked`, `waiting`, `pause` and `emptied`, and deltas over 3 s don't count. Failed reports are not resent (neither does the site; a resend could count twice), except one retry with a refreshed token after a 401: REST `POST https://api.class101.net/api/v1/playtime-tracking/lessons/<lessonId>/play` with `{ playbackLocation, interval: 10, timestamp, videoId: lesson.video.id }`. Auth is `authorization: Bearer <Firebase ID token>`, as the site sends it inside Class101's app webview; the website itself uses a session cookie. The API parses the JWT: a malformed token gets 401 `http/unauthorized`.
  - The site completes video lectures on the server from this watch time. It calls `completeLectureV3` only for lectures without video (and without a mission), and polls `lectureV2ById.completed` while playing. The app no longer calls it (v0.6.3 did on `ended`).
  - The REST API's CORS filter answers `Origin: null` (what a file:// app sends) with 403 "Invalid CORS request". So on the TV watch time always goes through `service/` (`rest`, path allow-listed, string fields and header values checked), with no fetch fallback. GraphQL falls back to fetch for a minute only when the Luna bus itself refuses the call (service missing). A mutation is never sent a second way: after any failure it is unknown whether the first try reached Class101 (Luna can answer "Message status unknown."), and it could apply twice. Every request has a deadline (Luna 25 s; `net.request` 20 s, response body included), so waiting for writes is bounded. Each login has its own id (`loginId()`: set at sign-in or hand-over, kept through token refreshes; an email can be missing). A queued write carries the login it was made under (the player passes the one it was opened with), and Home's cache belongs to one login. It is dropped, and not retried with a refreshed token, once another account has signed in. A Firebase token refresh only applies to the login that started it. The app signs out only when the login is really gone (`SESSION_EXPIRED`, `NO_SESSION`), not on a network failure while refreshing. A hand-over that meets a network failure keeps the login it was given and opens 내 클래스, and a newer hand-over wins over one still on the way. An HTTP error reply without data fails any GraphQL call. The class last-lesson lookup fails on any GraphQL error, because a failed `lastLesson` must not read as "none".
  - The site sends `setLessonProgress` only when the player closes or goes to the background. We also send it every 15 s and on pause. Position saves go out one at a time in the order they were made, across lessons, because each one moves the class's last lesson. Saves of one lesson still waiting merge into its newest position. A save is skipped only when it repeats the one just sent (same lesson and position, within 5 s). The player waits for that lesson's queued saves (`lessonSaved`) before reading where to resume.
  - Home keeps showing its cached list until in-flight writes finish (`settled()`), then loads. Klass shows the list at once and loads it again after the writes, asking Class101 for the class's last lesson (`classLastLesson`) instead of trusting what Home passed in; only that second answer counts as current. On both screens, 이어보기 acts only on a fresh answer. Pressed before that reload lands, it waits for it; if the reload's lookup failed, it asks again. Only one press is acted on at a time.
  - Reference TV, real account, 2026-11-23 (1.25x): `updateUserViewHistory` → true; `enterLecture` → `lastWatchedAt` = now, and `lastClass.lastAccessedAt` moved to that time (it was a day old, from before the user's v0.6.3 viewing); watch time → HTTP 200 every 10 s of content through the service. Not yet seen: a lecture finished by watch time alone, and `progressRatio` moving.
- `videoUrl` = CloudFront-signed HLS on private-cdn.class101.net (H.264 TS in 540p/720p/1080p, separate packed-AAC audio rendition plus a "vocals" one, no DRM); captions are WebVTT (ko/en/ja auto). `setLessonProgress` shows up in `lastLesson.video.progressSeconds`.
- Language: the gateway localizes titles by Accept-Language only, and webOS WAM overwrites that header with the TV menu language. So GraphQL goes through `service/` (JS service, Node v8.12 on the TV) with `accept-language: ko` and a User-Agent.

## Login hand-over (scripts/tv-login.mjs)

- Accounts without a password sign in on class101.net in a Chrome-family browser that the script starts with a temporary profile and `--remote-debugging-port`. It polls class101.net pages for the Firebase user in IndexedDB (`firebaseLocalStorageDb` / `firebase:authUser:*`), then deletes the profile and relaunches the TV app with `{ c101RefreshToken, email }` as launch params (`ares-launch -p`). App.jsx adopts them (`PalmSystem.launchParams` / `webOSRelaunch`).
- The IndexedDB probe aborts its upgrade so it never creates Firebase's database first.
- `--manual` prints a console snippet for the user's own browser; `--dry-run` skips the TV. test/login.mjs covers both against a local page (`C101TV_LOGIN_URL`, `C101TV_LOGIN_HEADLESS`).
- Why not sign in on the TV itself: class101.net's own pages need Chromium 94+ (webOS 5 has 68; an earlier attempt to run the site on the TV failed for that reason), and Kakao/Naver redirect only to class101.net.

## Speed playback (src/app/speedVideo.js, speedAudio.js, media.worker.js)

- LG limits (LG forum "TV app spec", confirmed on the reference TV): the native player off 1x mutes audio and trick-plays the picture; MSE ignores `playbackRate`, even video-only. So speeds ≠ 1 on HLS use our own pipeline; 1x stays native.
- Picture: fetch the video variant (≤720p; ≤540p above 1.5x), transmux TS→fMP4 with mux.js, divide tfdt/trun times by the rate (fmp4.js), append to MSE. The `<video>` plays 1x over a shorter timeline: media time = content time / rate. At 1080p the reference TV fell to 0.7x media speed (~23 fps decoded).
- Sound: the HLS alt audio rendition (packed AAC, not "vocals") → decodeAudioData → WSOLA (wsola.js) → AudioBufferSourceNodes at sample-exact times, locked to the picture clock (`SpeedVideo.contentTime()`).
- Both CPU jobs run in Web Workers from a blob: URL (`__MEDIA_WORKER__`, built by scripts/worker.mjs; blob workers work in file:// webOS apps). On the main thread, WSOLA took ~0.6 s per 5 s segment and blocked the page ~90% of the time.
- Sync: on webOS `video.currentTime` updates in ~200 ms steps and goes stale while the page is busy. Drift therefore uses the largest extrapolation of recent clock steps (steady readings are skipped: a stalled clock must not be extrapolated) and `AudioContext.getOutputTimestamp()`. Resync (an audible gap) only after 3 checks past 150 ms. A naive check restarted the sound every ~1.7 s (v0.4.x).
- Reference TV, v0.5.0, 720p, 1.25x: content 1.25–1.26 s/s, 0 resyncs, drift −13…−70 ms, no long tasks, 37.5 frames decoded/s but ~7.5/s dropped (the video plane shows ≤30 fps).
- Debug on the TV: `npm run inspect` and `window.__c101Player` (mode, `video`, `audio.drift()`, `audio.resyncs`). Chrome 68 has no `getVideoPlaybackQuality`: use `webkitDecodedFrameCount` / `webkitDroppedFrameCount`.

## Commands

- `npm run build` (release) / `npm test` (wsola unit test, dev build, test/e2e.mjs against a mock Class101 in Chromium 68, speed.mjs in Chromium 68, speed-e2e.mjs in Google Chrome for H.264/AAC, login.mjs) / `npm run deploy` / `npm run inspect` / `npm run extend`.

- `npm run tv:login` hands a browser login to the TV (TV on, app installed).

## Rules

- Never print, log or commit a user's password or tokens. The session (refresh token) lives only in the TV app's localStorage (`c101:session`).
- Key handling only for `event.isTrusted` events; screens claim keys with `useKeys()`, App.jsx handles defaults.
- Focus targets carry `data-fk`; App restores focus by key when popping back.
- No download or save features: the app streams like the website does.
